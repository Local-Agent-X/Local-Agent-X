# tool-execution

**Owns:** The dispatch pipeline every model-issued tool call passes through — resolve → policy (Ari + rule packs) → approval → sandbox → audit.
**Does not own:** Tool definitions and the registry → `src/tools/`; policy rows → `src/tool-policy/`; the kernel itself → `src/ari-kernel/`.
**Entry:** `index.ts` — `executeToolCalls` for model calls (the one entry; a test that needs one call's envelope uses `dispatch-one.test-helper.ts`); `executeHarnessCommand` (`harness-exec.ts`) for harness-initiated shell (build-verify, spec-probes, a built project's structure-check): kill switch + audit only, no policy/approval/RBAC; `dispatchApprovedCall` (`approved-call.ts`) to run a call the user approved from the inbox, through `executeToolCalls`.

## Invariants
- Never call a tool's `execute` from outside this module: the gates in `pre-dispatch.ts` and `enforce-policy.ts` are what make policy, Ari, approval and RBAC apply.
- Gate order in `enforce-policy.ts` (`securityAndValidationGates`) is load-bearing: name resolution runs before the kernel, so an unknown name reads as "not a tool", not as a kernel fault.
- A kernel-gated tool's kernel action is its row's `ariAction`, which the row type requires: one that fell through to `exec` was rejected by the kernel schema — a hard block under `ariRequired`.
- Model-supplied `_`-prefixed args are dropped (`internal-args.ts`); only `SESSION_SCOPED_TOOLS` get the trusted `_sessionId` (every tool with policy `pathArgs` is in it automatically), only `OPERATION_SCOPED_TOOLS` get `_operationId`; every call gets `_onEvent` and `_toolCallId`. A tool reads a stamp only through its accessor in `internal-args.ts` (`sessionIdOf`, `onEventOf`, `cwdOf`, …), never `args._x`, and only the dispatch pipeline writes one (`internal-args.test.ts` scans both). The stamps are never part of a call's identity: the side-effect journal fingerprints, the kernel bridge forwards and the approval card shows `withoutInternalArgs(args)`.
- A tool path argument is resolved with the call's session everywhere it is resolved: the file-access gate (`ctx.sessionId`), the tool (`sessionIdOf(args)`), and every check here about the same file (freshness, read-dedup, task-artifact pre-stat, the delete gates). Otherwise a work-rooted session gates `<workRoot>/x` and opens `<workspace>/x`. Guards: `agent-path-session.test.ts` (source scan), `test/work-root-gate-sink-parity.test.ts`.
- Every tool result the model reads is screened once, in the audit phase (`injection-exposure.ts`), never in a tool or a provider: the content is never edited, a note leads the rendered text, and harness text (the wrapper's frame, `read`'s warning) is never scanned.
- A tool message is built by `toolMessage()` (`tool-message-carry.ts`) and nothing else: the model reads its text, the harness reads its carry (`_status`, `_block`, `_media`, `_metadata`) through `toolMessageStatus` / `toolMessageBlock` / `toolMessageMedia` / `toolMessageMetadata`. `_metadata` is the result's whole metadata, every string (nested) through `scrubMetadata` (`redact` + `redactKnownSecrets`, the redaction the content gets on the wire), minus `stderr` when the content repeats it; `message-convert.ts` writes it back onto session rows and is the only other `_metadata` writer. A reader of `exit_code`, `duration_ms`, `taint_sources` or a media path reads the carry (absent → its own fallback), never the header or the text. Nothing new parses the `[status, k=v]` header back out of the text; `parseStatusHeader` / `parseResultHeader` serve rows persisted before the carry existed (2026-10-17) and nothing else. A refusal's `metadata.layer` is a `BlockLayer` (`src/types/tool-block.ts` `BLOCK_LAYERS`), which the type requires beside `recovery`. A plugin tool's refusal that names none is attributed at the audit phase to the plugin that owns the tool (`layer: "plugin"`, `plugin: <owner id>`, on the metadata and the block record); `"unknown"` is only a refusal with no owner at all, and the engine never writes it.
- An unattended run never pauses for a person. A gate that would need one parks the call in the user's inbox (`deferred-call.ts` `parkOrRefuse`) and the run goes on: the result stays status `blocked`, `metadata.layer` `"approval"`, marked by `metadata.deferredTo` (the item id, carried on the block record), with the gate's own reason. Never a new status, and never a loop guard reading the wording. A gate inside a tool (the browser's sensitive-page, download and CAPTCHA gates, the credential fill's first-use ask) cannot reach the inbox: it reads `unattendedCall(args)` off the `_callContext` stamp, returns its refusal marked `needsUser` (`src/tools/result-helpers.ts`) instead of raising a card into a sink nobody answers, and `run-sandboxed.ts` parks that result (`parkNeedsUser`). An attended run keeps the tool's refusal; the mark never reaches the model.
- The user's Approve is a one-shot grant on the ApprovalManager for that exact call in its session (`src/approval-call-grants.ts`), never a flag that skips gates. Each gate that would park, refuse or prompt for want of a person calls `takeUserGrant` first (the approval phase, the `secret_env` card, the unattended shell gate; `requestApprovalDetailed` takes it too); it sets `ctx.approvedByUser`. For a gate inside the tool, `run-sandboxed.ts` takes it before execute and stamps it as `_userGrant` (`userGrantOf`), which stands in for that gate's card. Every other gate re-runs. `dispatchApprovedCall` revokes the grant when the dispatch returns.
